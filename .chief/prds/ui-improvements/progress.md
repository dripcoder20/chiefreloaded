## Codebase Patterns
- **The authoring terminal is a real PTY — bytes written go straight to the agent's line editor.** The Go backend (`internal/session/authoring.go` → `authoring.Write`) writes raw decoded bytes to the PTY; it does no key interpretation. So any Enter/Shift+Enter/newline semantics must be decided in the frontend before `api.author.write`. xterm delivers Enter and Shift+Enter as the same key (default: both → CR). Intercept with `term.attachCustomKeyEventHandler` (return `false` to suppress xterm's default sequence, `true` to let it through). Keep the decision in a pure, unit-tested helper (`frontend/src/lib/terminalInput.ts`) and only wire it in the component. Convention: Enter → CR (`\r`, submit), Shift+Enter → LF (`\n`, insert line break). Guard IME via `event.isComposing` (Chromium webview reports it reliably) so composing candidates aren't read as Enter.
- **Implementation controls derive from authoritative state, never from a request result.** The store (`app.svelte.ts`) tracks a per-PRD `pending` transition map (`starting|pausing|resuming|stopping`) that overlays the last-known `RunSnapshot.state`; `app.displayState` and the `canStart/canResume/canPause/canStop` getters are the single source of truth for the toolbar. Actions (`startRun/pauseRun/resumeRun/stopRun`) guard on `pending[prd]` (no duplicate requests / at-most-one session) and reconcile via `reloadRuns()` on failure. Runes state-modules are tested from `*.svelte.test.ts` files that mock `../platform`.
- **Frontend is Svelte 5 (runes) + xterm inside a Wails v3 (Go) app.** All Go/Wails binding calls go through `frontend/src/platform/index.ts` (`api.*`), with an in-browser `mock.ts` stand-in used whenever not running in a real webview.
- **Tabs are driven by `app.view`** (`stores/app.svelte.ts`, values `stories | author | settings`). Rendering a view under `{#if app.view === ...}` unmounts it on tab switch and fires its `onDestroy` — use CSS visibility (a `hidden` class + `display:none`) instead when a view must survive a tab switch.
- **Quality checks:** `cd frontend && npm run check` (svelte-check) and `npm test` (vitest). Go side: `go build ./...`, `task test`, `task lint`.
- **Frontend tests:** vitest + jsdom + @testing-library/svelte. Config in `frontend/vitest.config.ts` (separate from `vite.config.ts` because the Wails runtime plugin can't load under jsdom). Setup stubs `ResizeObserver` in `src/test/setup.ts`. Mock `@xterm/xterm`, `@xterm/addon-fit`, and `../platform` in component tests.
- **Adding a new Go service method the frontend calls needs three edits + a codegen step.** (1) Session method in `internal/session/` (real logic, unit-testable against a temp dir via `newTestSession(t)` + `s.OpenProject(ctx, root)`; use `writePRD(t, root, name, body)` to seed PRDs). (2) A ≤5-line delegation on the matching `*Service` in `internal/services/services.go`. (3) Regenerate the TS bindings — they use `$Call.ByID(<hash>)` so they can NOT be hand-edited: run `go install github.com/wailsapp/wails/v3/cmd/wails3@v3.0.0-alpha2.121` then `PATH=$PATH:$(go env GOPATH)/bin wails3 generate bindings -ts`. `frontend/bindings/` is gitignored, so its changes never appear in `git status` and don't get committed. Then surface the method in `platform/index.ts` (`api.*`) AND add a mock impl in `platform/mock.ts`, or the browser build breaks. Opening a file / URL from Go uses `application.Get().Browser.OpenFile(path)` / `.OpenURL(url)` (guard `app == nil`, same pattern as `ProjectService.Pick`).
- **Svelte component visibility that is pure CSS (`:hover`, `:focus-within`, `@media (hover: none)`, opacity) can't be asserted in jsdom** — getComputedStyle doesn't apply stylesheet cascade or pseudo-classes, and the vitest svelte plugin doesn't inject the component `<style>` into the DOM either. Test the *mechanism* instead: the element is always rendered (not conditionally), is a real focusable control, and carries the right role/aria; note in a comment that the CSS reveal is verified visually.
- **Nested interactive elements are an a11y error (`<button>` in `<button>`).** A rail row that both selects (click) and has an overflow button must be a `<div class="row">` wrapping two sibling `<button>`s (a `.select` and a `.dots`), not one button. Use `.row:focus-within` to reveal the overflow button when either child is focused. A right-click handler on the static row div needs `<!-- svelte-ignore a11y_no_static_element_interactions -->` (it's a keyboard-accessible-button duplicate, so the shortcut is a pure enhancement); a `role="menu"` element needs `tabindex="-1"`.

## 2026-08-03 - US-001
- Implemented "Preserve PRD authoring sessions across tab changes."
- Root cause: `AuthorPane` was rendered under `{#if app.view === "author"}`, so any tab switch unmounted it, firing `onDestroy` which called `api.author.stop()` and disposed the terminal — killing the session and losing scrollback/state.
- Fix: `AuthorPane` is now always mounted in `App.svelte`'s pane and hides itself via an `active` prop (`class:hidden`) when it isn't the current view. The other views (Settings/Stories/blank) remain conditional and coexist with the hidden pane. `onDestroy` (and its stop-the-session behavior) now only fires when the pane is genuinely torn down (app close), which satisfies "closing releases resources; tab switching does not."
- Added an `$effect` in `AuthorPane` that refits the terminal when the tab becomes visible again (a `display:none` element has no geometry for xterm to size against).
- Files changed: `frontend/src/App.svelte`, `frontend/src/views/AuthorPane.svelte`, new `frontend/src/views/AuthorPane.test.ts`, new `frontend/src/test/setup.ts`, new `frontend/vitest.config.ts`, `frontend/package.json` (+ lock).
- **Learnings for future iterations:**
  - There is no explicit "close tab" affordance; the "close-session" behavior referenced by the story is `AuthorPane`'s `onDestroy` → `api.author.stop()`, plus the Stop / New session buttons. Keeping the component mounted makes tab switches a no-op for the session while preserving that close path on real teardown.
  - The authoring session is NOT tied to `app.selectedPrd` — selecting another PRD only changes what the "Edit" button would start; it never re-attaches a terminal. So AC "selecting another PRD doesn't attach to the preserved session" holds for free.
  - This repo had **no frontend test runner** before this story; vitest was added. Component tests must mock xterm (jsdom has no canvas) and stub `ResizeObserver`. Model a "tab switch" by toggling the `active` prop via `rerender`, and "closing the tab" by `unmount()`.
  - `@sveltejs/vite-plugin-svelte` in the vitest config: don't pass `{ hot: false }` (invalid option warning); just `svelte()`. Cast the plugin to `any` because vitest bundles its own Vite whose plugin types differ from the app's Vite 8.
